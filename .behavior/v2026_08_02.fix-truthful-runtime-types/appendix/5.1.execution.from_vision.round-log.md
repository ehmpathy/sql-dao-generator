the full unit suite reported the two `generate` tests as **timeouts** (71s past a 60s bound). the

**the lesson: a timeout is not a diagnosis, it is the absence of one.** I had a plausible story for

this is the same failure shape as the `nest`/`reference` error earlier in this route: a confident

### the new `.utils/` directory was gitignored, and CI would have caught it after I did not

a hazard the suite could never surface, because it is invisible to a working tree.

`exampleProject/.gitignore` carried `src/access/daos` — a rule that predates the generated dao
files, all **78** of which are nonetheless **tracked**. that is deliberate: a fresh clone must
typecheck without a codegen run first.

the reason the rule bound `.utils/` and no extant file is **not** that it "applies only to what
came after it" — a gitignore rule has no notion of when a file was added. it is that git **does
not untrack what it already tracks**, so a rule over a fully-tracked directory is inert against
every file in it and live only against files that do not yet exist. `.utils/` was the first such
file set, so it was the only generated output the rule ever caught — and every
`import { asDateFromDbValue } from '../.utils/asDateFromDbValue'` in the tracked daos would have
pointed at a file a fresh checkout does not have.

local green proves the opposite of what it looks like here: the files are on **my** disk, so
`tsc` was happy while CI would have failed on the first clone.

**the first repair was a patch, and the `has-pruned-backcompat` self review struck it.** it kept
the rule and bolted two negations on, which needed a git subtlety to work at all — git will not
descend into an excluded parent, so the `/**` form is required for a negation to be reachable:

```gitignore
src/access/daos/**          # <- the patch. removed 2026-09-09
!src/access/daos/.utils/
!src/access/daos/.utils/**
```

**the rule was dead, and the check took one command.** `git status --ignored` over that
directory returns **zero ignored entries** — all 78 generated dao files are tracked, and git does
not untrack what it already tracks. so the rule could never ignore a file that exists; its one
live effect was to swallow the *next* directory added under that path, which it did to `.utils/`.

⇒ **the rule is now removed outright**, with a note in its place that says why there is none.
proof the removal is safe: `git status --ignored` is byte-identical before and after — 27 `M`, one
`??`, zero files changed status. only files that do not yet exist behave differently, which is
the aim.

⇒ **the general shape: a new generated directory inherits whatever ignore rules already cover its
parent, and no test can see it.** `git status` showed `.utils/` as `??` after the first repair,
which is the only check that would have caught it — and the second repair is what stops the next
directory from a toll it need not pay.

🟡 **the sharper lesson is about the FIRST repair, not the rule.** a negation laid over a rule
made the symptom go away and left the trap armed. the question that would have caught it at the
time — *"what does this rule actually ignore today?"* — is one command, and I did not ask it until
a self review forced the artifact open.

### 🟡 correction to a vision edgecase — the fractional-numeric promise holds on ONE arm

the vision's edgecase table carries this row:

> **a fractional `numeric` past float precision** — unchanged from today (low-order digits lost);
> the guard is integral-only, so a deployed read does not become an outage

**that is true on the string arm and false on the number arm**, and the difference is not a
defect in the caster — it is undecidable there.

| how the value arrives | what `asNumberFromDbValue` does |
| --- | --- |
| `'9007199254740993.5'` — a raw read, **no** pg parser | returned as `9007199254740994`, unchanged from today ✅ |
| `9007199254740993.5` — a json read, **or** a raw read **with** the `parseFloat` parser | **throws** ❌ |

**why.** the fraction survives only in the *source text*. by the time the value is a `number` it
has been through `JSON.parse` or `parseFloat`, and `9007199254740993.5` and a truncated bigserial
`9007199254740993` are the **same double** — `9007199254740994`. the caster cannot part them, so
it throws rather than hand back what may be a wrong id.

⇒ **the population this reaches is the one that follows our own recommended configuration** — a
consumer with the pg parsers installed, which is the ehmpathy convention and what the generated
supply encourages. that is the sharp part, and the vision's row did not say it.

**what changed here: a test, not the behavior.** the throw is the right call — `term=cast`'s own
invariant forbids a wrong-but-plausible value. what was absent is the clamp: the string arm was
pinned and the number arm was not, so the asymmetry was incidental rather than declared. it is now
pinned by a paired test (`defineDaoUtilAsDbValueCodeFiles.test.ts`, *"the SAME fractional value,
but already a number"*), so a future refactor that "unifies" the two arms breaks one of the pair.

🔴 **for the wisher, since it bounds an approved claim:** this narrows the vision's stated residual
rather than contradicts its reasoning — the vision already priced "a fractional `numeric` beyond
float precision still loses low-order digits" as a real limit of `number` as the declared domain
type, and named `iso-price` as the right home for a money column. this adds that on two of the
three paths the loss is now a **throw** rather than a silent imprecision. no acceptance line moves.

⇒ found by the `has-pruned-backcompat` self review, from a read of the caster's own `.note`

## the casts' fail-loud contract, as it now stands

the i003 peer round put **six** lanes on the two `as*` casts, and their union is what the table
below records. it is stated here rather than left across five `.taken` files, because a reader who
wants to know what a generated cast refuses should find it in one place.

| the input | the arm | verdict |
| --- | --- | --- |
| a `Date` | idempotent | returned unchanged |
| an iso-8601 string | parse | a `Date` |
| a string that does not open `YYYY-MM-DD` | **iso-prefix guard** | throws |
| an iso-shaped string this runtime cannot parse | NaN guard | throws |
| a `number` | idempotent | returned unchanged |
| a numeric string | parse | a `number` |
| a blank string | **blank guard** | throws — `Number('')` is `0`, and a wrong number is worse than a thrown one |
| a non-numeric string | NaN guard | throws |
| `'Infinity'`, `'-Infinity'`, `'1e999'` | **finite guard** | throws |
| an **integral** value past `Number.MAX_SAFE_INTEGER` | safe-integer guard | throws |
| a **fractional** value past float precision, as a string | — | returned, low-order digits lost |
| the same value, already a `number` | safe-integer guard | throws — the fraction is gone by then |

every throw is a `DbValueCastError` that names the property, the value, **and the fix**. all twelve
rows are clamped by unit cases, and the six error messages are pinned by snapshots as well as by
fragment assertions.

🟡 **three of these guards take deliberately asymmetric scopes, and the asymmetry is the design:**

- the **finite** guard is not scoped to integral values, where the safe-integer guard beside it is.
  a fractional value past float precision is *approximately* right, so to throw on it would turn a
  deployed read into an outage; a non-finite value is *categorically* wrong
- the **iso-prefix** guard is a prefix match, not a full format. the offset, the fractional seconds,
  and the `Z` / `+hh:mm` forms vary by column type and server config, so a full enumeration would
  reject a valid form we did not predict. clamped by 4 negative controls, which are the half that
  proves it did not overreach
- the **safe-integer** guard reads integral-ness off the *source*, so its two arms diverge on one
  input. pinned by a paired test, so a refactor that "unified" them breaks one
