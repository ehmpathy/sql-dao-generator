## what shipped

one change, five parts:

| part | what | breaks runtime? |
| --- | --- | --- |
| **A. truthful types** | a `Strict` / `Jsoned` shape pair per dao; the cast takes their union | no |
| **B. one runtime type** | the shared casts module; every DATE / NUMBER read is cast | **yes** — values change |
| **C. proof** | the nested-`Date` fixture + a parser-free connection fixture | no |
| **D. the pg type-parser supply** | `setDbTypeParsers`, exported inert | no |
| **E. the legible break** | readme break notice + release-note text | no |

### A. truthful types

- each dao's `castFromDatabaseObject.ts` exports `SqlQueryFind<X>ByIdOutputStrict` — a re-export of
  the upstream shape, or `Omit<raw, nested> & { nested: ...Jsoned }` where the dobj nests another
- a domain **literal** also exports
  `...OutputJsoned = AsJsonFromDbObject<Pick<...Strict, keys>>` and
  `...Output = Strict | Jsoned`. an entity gets `Strict` alone
  (`rule.require.jsoned-shape-only-for-literals`)
- the `Pick` fails loud at compile time if the nested select's key set drifts. both the `Pick` and
  the read sites derive the column name from one transformer, so a declaration-ref
  (`carriageRef` → `carriage_uuid`) cannot split them
- the array arm keeps the cardinality correction: `COALESCE(..., '[]'::json)` guarantees an array
  where upstream types a nullable object
- definer: `defineDbObjectShapesForCastMethod.ts`

### B. one runtime type

the casts module is `src/access/daos/.generated/casts.ts`, defined by `defineDaoCastsCodeFile.ts`
and one `defineDaoCastsSection*` definer per section:

| export | what |
| --- | --- |
| `asFromDatabase.date` / `.number` | the two casts; implementations `asDateFromDbValue` / `asNumberFromDbValue` |
| `DbValueCastError` | the throw; names the property, the value, and the fix |
| `AsJsonFromDbObject` | the type helper that derives `Jsoned` from `Strict` |
| `isIntegralDbValue` | reads integral-ness off the source, for the safe-integer guard |
| `setDbTypeParsers` + `DbTypeParserCollisionError` | part D |

- call form: `asFromDatabase.number({ value: dbObject.id, property: 'id' })`. named args, since the
  vision's own edgecase row requires the throw to name the property
- the module sits in `.generated/`: a plain `.ts` elsewhere under `src/access/daos/` is scanned for
  sql by the consumer's `sql-code-generator` config and fails their generate run
  (`rule.forbid.invented-output-dirs`)
- each cast is idempotent — a `Date` or `number` is returned by reference
- a nullable property short-circuits before the cast, on the scalar and the elementwise array branch
- a dao imports only what it uses; `getOneCastNameForProperty` feeds both the imports and the
  property code, so they cannot drift
- `Date[]` / `number[]` cast elementwise — unreachable until `sql-schema-generator`'s `ARRAY_OF`
  accepts native primitive arrays
- **upsert is a third serialization site.** it read `id` and `created_at` off the upsert function's
  own select, uncast, so a parser-free connection returned `id` as a `string` from `upsert` and a
  `number` from `findById`. `defineDaoUpsertMethodCodeForDomainObject.ts` now casts both, via
  `getAllCastNamesForUpsert` — the same lookup the cast definer uses. `uuid` stays a direct read
- `id?: string` in a domain is refused upstream at
  `defineSqlSchemaRelationshipForDomainObject.ts` — every reserved db-generated property is checked
  against its column type. the throw had no coverage; four tests now pin it

### C. proof

- `generate.integration.test.ts` reads one row through both paths and asserts one value, one type
- `getDbConnectionWithoutTypeParsers.ts` + a block that swaps oid 20 / 1700 to pass-through text and

  - its first assertion is the teeth: `SELECT 1::bigint, 1.5::numeric` must return two `string`s,

  - it also executes the vision's one `[research]` item: a `json_build_object` → `JSON.parse` →

- `daoCasts.behavior.test.ts` imports the **generated** module, never a copy, and first asserts the

### D. the pg type-parser supply

- `setDbTypeParsers()` touches no global until called. oids: 20 (`int8`), 1700 (`numeric`), 1016
  (`int8[]`). `timestamptz`, `numeric[]`, and `uuid[]` already yield the right shape
- each oid is probed with a sample before the write: a correct parser is skipped (idempotent), a
  node-postgres default is replaced, a foreign parser that disagrees throws
  `DbTypeParserCollisionError`. the comparison is behavioral — parser identity does not compare
  across module instances
- the int8 parser refuses a value past `Number.MAX_SAFE_INTEGER`, and the numeric parser refuses a
  bare `.`
- an `int8[]` NULL element yields `null`, as node-postgres' own parser does. `parseInt('NULL')` is
  `NaN`, and the parser is process-global
- no oid-114 reviver: its dispatch is not exact, so it would reach every json value in the process
- the opt-in is documented in the readme (`#### the pg type parsers — supplied, never applied`);
  `generate` prints no reminder

### E. the legible break — wish acceptance #5

- `readme.md` `### Truthful Runtime Types`, with `#### what moves when an extant project regenerates`:
  the nested `Date`, the parser-free `string` → `number`, and the new **throw** where a value the
  declared type cannot hold used to return quietly
- the release-note text, for whoever commits:

  > *a generated dao now converts every DATE and NUMBER value at the persistence boundary, so it
  > returns the runtime type your domain object declares from every query. three values move for
  > extant consumers — see `readme.md`'s "what moves when an extant project regenerates". the casts

## the casts' fail-loud contract

| the input | the arm | verdict |
| --- | --- | --- |
| a `Date` | idempotent | returned unchanged |
| an iso-8601 string | parse | a `Date` |
| a string that does not open `YYYY-MM-DD` | iso-prefix guard | throws |
| an iso-shaped string this runtime cannot parse | NaN guard | throws |
| a `number` | idempotent | returned unchanged |
| a numeric string | parse | a `number` |
| a blank string | blank guard | throws — `Number('')` is `0` |
| a non-numeric string | NaN guard | throws |
| `'Infinity'`, `'-Infinity'`, `'1e999'` | finite guard | throws |
| an integral value past `Number.MAX_SAFE_INTEGER` | safe-integer guard | throws |
| a fractional value past float precision, as a string | — | returned, low-order digits lost |
| the same value, already a `number` | safe-integer guard | throws |

every throw is a `DbValueCastError`. each row is clamped by a unit case; the messages are pinned by
snapshot.

- the **finite** guard spans fractional values; the **safe-integer** guard does not. a fraction past
  float precision is approximately right, so a throw would turn a deployed read into an outage; a
  non-finite value is categorically wrong
- the **iso-prefix** guard is a prefix match: offset, fractional seconds, and zone forms vary by
  column type and server config. four negative controls prove it does not overreach
- the **safe-integer** guard reads integral-ness off the source, so its arms diverge on one value. the
  fraction survives only in text; after `JSON.parse` or `parseFloat`, `9007199254740993.5` and a
  truncated bigserial are the same double. a paired test pins the asymmetry
  - ⇒ the throw reaches a consumer who follows the recommended parser convention. it narrows the
    vision's stated residual: on two of three paths the loss is now a throw, never a silent
    imprecision
