# wish: generated daos yield ONE runtime type per column, and the types tell the truth

## .what

two outcomes, and the second rests on the first:

1. **a given column type maps to exactly ONE runtime type across every generated query.**
   today the same field arrives as a different javascript type per how the generated query
   happens to select it.
2. **the generated `types.ts` states what actually arrives at runtime** — not what the
   logical sql type suggests.

## .why

**the generated types currently lie, and the lie carries weight.**

a consumer cannot write a correct boundary cast against a type that already claims the
value is the right shape. the cast reads as a redundant no-op, the compiler agrees, and a
forgotten leaf fails silently. so consumers are pushed to one of two bad places:

- coerce at the domain-schema declaration — which puts a persistence concern inside the
  domain model and makes the declaration itself lie
- hand-cast at every leaf — unenforced by the compiler, silent when missed

both are workarounds for a defect that lives in the generator. this wish moves the
correctness to where the knowledge already sits: the generator knows the column type AND
which serialization it chose.

## .what was verified (2026-08-02, in `ahbode/svc-notifications`)

ground to save you a search — **not instruction.** see `.the HOW is yours` below.

### the same field, two runtime types

| field | raw column select | nested via `json_build_object` |
|---|---|---|
| `id` (bigserial) | **string** — node-postgres returns int8 as string (precision > 2^53) | **number** — a json number |
| `created_at` (timestamptz) | **Date** — node-postgres parses oid 1184 | **string** — json has no Date type |

both observed in generated `findById.ts` files in one repo:

- `agentDao/findById.ts` selects **raw columns**
- `smsDao/findById.ts` embeds agent + media via **`json_build_object` / `json_agg`**

### the sharpest tell

`agentDao.castFromDatabaseObject` is invoked from **both** paths — directly (raw:
`created_at` = Date) and as the nested cast inside sms / voiceCall / assignment (json:
`created_at` = string). **one cast function, two contradictory input shapes.**

meanwhile the generated `types.ts` declares `id: number` and `created_at: Date`
**uniformly** for every query output — which matches neither serialization consistently.

### the historical evidence that this is the true cause

a joi → zod migration in `svc-notifications` exploded on exactly this. joi silently
coerced both string forms; strict `z.date()` / `z.number()` reject them, so
`expected date, received string` threw on every json-nested hydration. `z.coerce.*`
"fixed" it only by absorption of the divergence — the defect was masked, not removed.

that repo has since **reverted** its coercion rip-out and holds strict schemas PENDING
this fix, rather than sprinkle unenforced per-leaf casts.

## .acceptance

- a given column type maps to ONE runtime type across all generated queries — the raw
  path and the nested path no longer disagree
- the generated `types.ts` matches what is actually received at runtime
- a consumer can declare a strict domain schema (no coercion) and have any mismatch be
  **compiler-enforced**, not a silent runtime surprise
- a cast function reachable from more than one query path receives one consistent shape
- extant consumers keep their behavior, or the change ships such that the break is
  explicit and legible — this generator has downstream repos

## .the HOW is yours — advisory only

per `rule.require.wish-outcome-over-proposal` and `rule.forbid.prescribe-how-on-dispatch`,
`.what` / `.why` / `.acceptance` are authoritative. all under "what was verified" is
**ground, not instruction.** every design decision is yours, in particular:

- **which direction uniformity goes** — a real fork with real tradeoffs, and yours to
  settle. json-everywhere and raw-everywhere each carry costs (precision, query shape,
  performance, migration blast radius). the outcome demands consistency; it does NOT
  demand a particular side.
- **where the truth is told** — a truthful emitted type, a normalization at the generated
  boundary, or both. the acceptance asks that a mismatch be compiler-enforced; it does not
  name the mechanism.
- **whether this is one change or several** — and whether any part is a break-level release

`ehmpathy/sql-dao-generator` issue **#61** carries the original write-up. read it as
context, but note it was authored from OUTSIDE this repo by a consumer, and it proposes a
specific three-step fix. treat that proposal as one party's guess, not as the spec. if an
in-repo pattern beats it, prefer that and say why in your vision yield.

## .open questions worth a decision (yours to settle)

- is bigint-as-string actually the *correct* runtime type to expose, given that json's
  number cannot hold the full int8 range? a "consistent" choice that silently truncates
  large ids would satisfy the letter of uniformity and fail its intent.
- do extant consumers rest on the current (inconsistent) shapes in ways that make a clean
  cutover impossible? if so, that is worth surfaced early.
