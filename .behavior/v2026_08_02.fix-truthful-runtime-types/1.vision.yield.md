# vision: sql-dao-generator — one runtime type per column, and types that tell the truth

## tl;dr

a generated dao **establishes** the runtime type of every value it hands back, rather than
**assumes** one.

- today one column arrives as a different javascript value per how the query selected it (raw
  column vs `json_build_object`)
- the generated `castFromDatabaseObject` covers the gap with an `as` that claims a shape the value
  does not have
- after: the cast **converts** every divergence-prone value at the persistence boundary — the one
  place that knows both the domain type and the serialization it chose
- ⇒ a dao's output is one shape, and a consumer holds a strict `z.date()` / `z.number()` schema with
  no coercion anywhere

---

## the outcome world

### day-in-the-life

a consumer models media on a text message. media has no identity of its own, so it is a **domain
literal**:

```ts
export interface SmsMedia {
  id?: number;
  createdAt?: Date;        // timestamptz column
  mime: SmsMediaMime;
  urlReceived: string;
}
export class SmsMedia extends DomainLiteral<SmsMedia> implements SmsMedia {}

export interface Sms {
  id?: number;
  media: SmsMedia[];       // a nested LITERAL array -> arrives as json
  body: string;
}
export class Sms extends DomainEntity<Sms> implements Sms {}
```

> only a literal may be directly nested — the generator throws
> `DirectlyNestedNonDomainObjectReferenceForbiddenError` on a nested entity
> (`defineSqlSchemaReferenceForDomainObjectProperty.ts:171-188`). so the json serialization, and this
> whole defect, is reachable **only** through a nested literal. an entity by `Ref` selects a `.uuid`
> `varchar`, a `string` on every path.

with a strict schema on `SmsMedia` — `z.date()`, no `z.coerce.*` — both of these hold:

```ts
const mediaDirect = await daoSmsMedia.findById({ id: 1 }, context);
const smsNested   = await daoSms.findById({ id: 9 }, context);

mediaDirect.createdAt instanceof Date;             // true
smsNested.media[0]!.createdAt instanceof Date;     // true  <- today: false, it is a string
typeof mediaDirect.id === 'number';                // true
typeof smsNested.media[0]!.id === 'number';        // true
```

the array case (`json_agg`) carries three untruths, in two places:

| untruth | whose | what it says | what arrives |
| --- | --- | --- | --- |
| element shape | the **`as` assertion** we generate | the raw-row type `SqlQueryFind<X>ByIdOutput` | a json bag |
| cardinality | the **generated type** (`SqlFunctionJsonBuildObjectOutput`) | an object | an array |
| nullability | the **generated type** | may be `null` | never `null` — `COALESCE(..., '[]'::json)` |

the `as X[]` is right about cardinality and non-nullness and wrong about the element. the solo case
(`json_build_object`) carries only the element-shape untruth.

### before / after

| aspect | before | after |
| --- | --- | --- |
| `createdAt` (timestamptz) via raw select | `Date` | `Date` |
| `createdAt` via nested json | `string` (ISO) | `Date` |
| a `numeric` property via raw | `string` — unless the consumer installed a pg type parser | `number` |
| a `numeric` property via nested json | `number` | `number` |
| `id` (bigserial) via raw | `string` — unless the consumer installed a pg type parser | `number`, or a loud error past `2^53` |
| `id` via nested json | `number` (silently lossy past `2^53`) | `number`, or a loud error past `2^53` |
| one cast, two callers | receives two contradictory shapes | receives either, returns one |
| the nested `as` (solo and array) | claims the raw-row shape of a json bag | claims the json shape it has |
| the generated **type** under a `json_agg` column | `Record<string, any> \| null` where a non-null array arrives | `X[]`, non-null |
| consumer's domain schema | must coerce, or lie | strict, and honest |
| consumer's pg connection | must install `setTypeParser` or the daos misbehave silently | the daos work either way |

### the constraint the design turns on

> the generator **cannot know** the runtime type from the sql type alone — so it must **establish** it.

two independent unknowns sit between a postgres column and a javascript value:

1. **which serialization** the query used. json has no `Date`, so a `timestamptz` inside json is
   necessarily a string
2. **which type parsers** the consumer installed. by default node-postgres returns `bigint` and
   `numeric` as strings; the ehmpathy convention overrides both, but ambiently and undocumented

a static `bigserial -> number` map guesses both. the cast knows the declared type and sits where it
can convert — so the truth is not a fact to *report*, it is a fact to *make true*.

## user experience

### usecase

> "i model `createdAt: Date` and `id: number`. i want a dao that gives me a `Date` and a `number` —
> from every query, on every machine, with no coercion in my domain model."

### contract inputs & outputs

- **input**: the hydrated `DomainObjectMetadata` plus the `SqlSchemaToDomainObjectRelationship`,
  which already carries `isNullable`, `isArray`, and `reference` per property
- **output**:
  - per dao: a `castFromDatabaseObject` that converts, plus its `...Strict` shape and — for a literal
    — its `...Jsoned` shape and `...Output` union (`rule.require.jsoned-shape-only-for-literals`)
  - one shared module, `.generated/casts.ts`:
    - `asFromDatabase` `{ date, number }` — applied by every generated cast
    - `DbValueCastError`, `AsJsonFromDbObject`
    - `setDbTypeParsers` + `DbTypeParserCollisionError` — **supplied, never applied**

the dot-prefixed `.generated/` is the one dir a consumer's `sql-code-generator` glob skips, so a
plain `.ts` there is never scanned for sql (`rule.forbid.invented-output-dirs`).

the cast body changes from pass-through to conversion, **only** where values diverge:

```ts
// before — true on one path, false on the other
createdAt: dbObject.created_at,
id: dbObject.id,

// after
createdAt: asFromDatabase.date({ value: dbObject.created_at, property: 'createdAt' }),
id: asFromDatabase.number({ value: dbObject.id, property: 'id' }),
```

each cast is fail-loud, never silently coercive:

- `date` — a `Date` passes through (idempotent); a string is parsed; an unparseable one throws
- `number` — a `number` passes through; a string is parsed; `NaN` throws; an **integral** value past
  `Number.MAX_SAFE_INTEGER` throws

**the safe-integer guard is integral-only.** a guard on every value past `2^53` would make a
`numeric(30,10)` that loses low-order digits today **throw on read** — an outage traded for an
imprecision. integral-only catches the `bigserial` id and leaves fractional precision as it is.

🟡 **the two input arms diverge at this bound.**

- a string arm reads integral-ness off the source, so a fractional string past float precision
  returns, lossy as today
- a number arm arrives after `JSON.parse` / `parseFloat`, with the fraction already gone —
  `9007199254740993.5` and a truncated id are the same double
  - ⇒ it throws rather than hand back what may be a wrong id
- a paired test in `daoCasts.behavior.test.ts` pins the asymmetry

`string`, `boolean`, `uuid`, and `enum` agree across both serializations and get no cast. the
surface is **DATE and NUMBER**, solo and in arrays.

### timeline

1. `introspect` → metadata says `createdAt` is `DATE`, `id` is `NUMBER` (unchanged)
2. `defineQuerySelectExpressionForSqlSchemaProperty` → a raw column or a json expression (unchanged —
   no sql, no view, no migration churn)
3. `defineDaoUtilCastMethodCodeForDomainObject` → wraps DATE / NUMBER reads in `asFromDatabase.*`,
   and types the input as the truthful shape union (**the change**)
4. `defineDaoCastsCodeFile` → the shared `.generated/casts.ts`
5. consumer regenerates → one output shape, on every path, on every machine

## mental model

- to a friend: *"the database can hand the same field back as a `Date` or a string per how the query
  was written. the dao passed along whatever it got and claimed it was a `Date`. now it converts it."*
- analogy: **a currency desk at the border.** two travellers arrive by different routes, one with
  coins, one with notes. the old dao stamped both "coins." the new one exchanges: whatever you arrive
  with, you leave with one denomination

| they say (consumer dev) | we say (this repo) |
| --- | --- |
| "it comes back as a string sometimes" | the two serializations diverge for this column type |
| "the nested one is different" | the `DIRECT_BY_NESTING` path — a nested domain **literal**, via `json_build_object` / `json_agg` |
| "the type says `Date` but it's a string" | the generated `as` on a json bag |
| "i had to add `z.coerce`" | the divergence was absorbed downstream instead of at-cause |

## evaluation

### against the wish's acceptance

| acceptance | met? | how |
| --- | --- | --- |
| one runtime type per column across all queries | **yes, at the dao contract** | the cast converts both serializations into one |
| generated types match what arrives at runtime | **yes** | the cast's input is typed as the true shape union |
| a strict domain schema, mismatch caught not silent | **yes at runtime, partly at compile time** | see caveat 2 |
| a cast reachable from >1 path receives one shape | **yes, by absorption** | it accepts either and returns one |
| extant consumers keep behavior, or break legibly | **mostly kept** | with the pg parsers installed, only json-nested dates change (the fix). without them, values silently wrong today become right |

**two caveats.**

1. "one runtime type" holds at the **dao boundary**, not on the **wire**. a raw `timestamptz` still
   crosses the socket as a `Date` and a nested one as a string. see the fulcrum
2. **compiler enforcement is out of reach from this repo.** upstream types the json bag
   `Record<string, any>`, assignable to every type, so no assertion we generate makes the compiler
   object. what ships: the declared type is true, and a mismatch throws at the boundary. full
   enforcement needs `sql-code-generator` to type `json_build_object` subqueries
   (`handoff.sql-code-generator.md`). a consumer who read "compiler-enforced" and dropped their
   runtime schema would be worse off than today

### pros

- **smallest blast radius that delivers the outcome** — no sql changes, no view rewrites, no
  migration for any downstream repo
- **kills a hidden dependency** — dao correctness no longer rests on a `setTypeParser` call in a
  file the generator never sees
- **at-cause** — the conversion sits at the persistence boundary, not in the domain model or at leaves
- **fail-loud** — an `id` past `2^53` raises instead of truncates
- **forward-compatible** — a cast that accepts `Date | string` stays correct under any later wire
  choice

### cons

- **the wire stays mixed.** a reader of `.generated/types.ts` or a hand-rolled query still meets two
  serializations; the supplied parsers serve that case, and only if opted into
- **one new generated module**, `.generated/casts.ts`, on a consumer's first regeneration
- **the parser supply can be left un-opted** — the deliberate cost of a supply that refuses to mutate
  a process-global on the consumer's behalf
- **`numeric -> number` is a float.** a money column belongs in `iso-price`; flagged, out of scope
- **a per-value function call** on DATE/NUMBER reads — negligible against a round trip

### edgecases

| edgecase | intended behavior |
| --- | --- |
| `createdAt` via raw select (already a `Date`) | passed through — the cast is idempotent |
| `createdAt` via nested json (ISO string) | parsed to `Date` |
| `createdAt?: Date \| null` | `null` short-circuits before the cast |
| `Date[]` / `number[]` (native arrays) | converted elementwise |
| `id` past `Number.MAX_SAFE_INTEGER` | **throws**, on either path |
| a fractional `numeric` past float precision, as a string | returned, lossy as today |
| the same value, already a `number` | **throws** — indistinguishable from a truncated id |
| a domain that declares `id?: string` | refused upstream: `defineSqlSchemaRelationshipForDomainObject.ts` checks every reserved column against its type and throws `UserInputError`, so it never reaches dao codegen. ⇒ only DATE and NUMBER diverge, with no exception |
| a `timestamptz` with microsecond precision | both paths land on a millisecond `Date` — "one runtime type" holds at ms resolution |
| an unparseable date string | throws, with the value and the property named |
| `string` / `boolean` / `uuid` / enum / `uuid[]` | untouched — identical across both serializations |
| a nested **entity** (by `Ref` or `xUuid`) | no divergence, no cast — a `.uuid` `varchar` select |
| a nested entity written as a bare `x: X` | already forbidden at codegen |
| an empty nested-literal array | `[]`, never `null` — `COALESCE(..., '[]'::json)` |
| a `bytea` column | unreachable from a declared property — a domain `string` maps to `varchar` even when named `...Hash` |
| a dobj nested 2+ levels deep | each level's cast converts its own values; no special case |

## the fulcrum — which direction uniformity goes

| direction | what it means | verdict |
| --- | --- | --- |
| **json everywhere** | wrap top-level selects in `json_build_object` | `id` becomes silently lossy past `2^53`, and every column loses its type to `Record<string, any>` |
| **raw everywhere** | drop json nests; hydrate via separate queries or lateral joins | typeable, but a rewrite of query architecture and a certain break |
| **uniform at the connection layer** | an oid-114 reviver revives date fields inside every json blob | proven in `svc-notifications`; loses on three grounds below |
| **uniform at the dao boundary** ✅ | keep both serializations; the cast converts both into one | every acceptance outcome, no sql churn, compatible with any later wire |

**settled by the wisher: the dao boundary.** a cast written `Date | string -> Date` is correct under
the mixed wire, a json-everywhere wire, and a raw-everywhere wire — the move that survives all three.

### why not the connection-layer reviver

`svc-notifications` ships one, keyed on the `*_at` field **name**, and it is green.

1. **it guesses what this generator knows.** `expiry: Date` has no `_at` suffix and is missed; a
   `varchar` named `signed_at` is wrongly converted. the metadata says `DATE` outright
2. **a process-global reviver cannot know which table a blob came from.** `pg.types` dispatches on
   oid alone, so it reaches every json/jsonb value — a stored third-party payload with its own
   `created_at` string becomes a `Date`. that hazard is live in `svc-notifications` today
   (`handoff.svc-notifications.md`)
3. **it cannot satisfy acceptance #2.** it repairs the value and leaves the untruth this repo
   generates. the two answer different halves

their success corroborates the diagnosis: they report the json blob was the one real gap.

### the pg type-parser supply — a complement, settled by the wisher

**codegen the parsers**, over a readme paragraph: prose drifts from the schema, generated code does
not.

**why it is not a substitute.** a `json_build_object` column arrives as one oid-114 value; postgres
already flattened the inner `created_at` to a json string, so no oid 1184 exists on the wire to
register against.

**why it earns its place:**

- **the correct set is derivable, not memorable** — `svc-notifications` registers oids 20 + 1700,
  this repo's example project 20 + 1016 + 1700. same org, two subsets: the convention already drifted
- **hand-written queries need it** — the casts touch dao output only
- **opt-in bounds the blast radius** — `setTypeParser` mutates a process-global registry

**two constraints follow.**

- **supply, never apply** — export a named operation; mutate naught at import (`term=supply`)
- **fail loud on a collision** — last write wins silently in `pg.types`, so `setDbTypeParsers` reads
  the extant parser per oid and throws `DbTypeParserCollisionError` where one differs. a design that
  exists because registrations drift must not assume its own is alone

**no oid-114 reviver in the supply.** scalar parsers dispatch on the column's own oid and reach
exactly those columns; a reviver reaches every json value in the process. the daos do not need one —
the casts cover every dao path. the readme documents the reviver as a pattern, with the hazard named.

**rejected: register oid 1184 to return the raw string.** uniform, and uniformly wrong — the domain
declares `Date` and would receive a string on both paths.

**the rework, if wire uniformity is wanted later:** additive, not a teardown. select the
divergence-prone columns as text on both paths (`id::text`, `to_json(created_at)#>>'{}'`); the casts
stay correct. cost: a regeneration of views and types for every downstream repo. not this route.

## open questions & assumptions

### assumptions

1. **the domain declaration is the target shape.** `createdAt: Date` means the dao owes a `Date`
2. **`id` stays `number`.** every extant domain declares `id?: number`; bigint-as-string would be
   safer and would break them all. a guarded `number` gets the safety without the break
3. **the casts ship as generated code, not a runtime dependency.** consumers already import from
   `.generated/`. whether to extract a package is fulcrum F12
4. **only DATE and NUMBER diverge.** the generator picks the column from the declared type, and the
   one candidate exception (`id?: string`) is refused upstream
5. **the casts are idempotent on the raw path** — tested directly, since "raw-path consumers see no
   change" rests on it

### the [wisher] set — all five settled

| # | question | guess | decision |
| - | --- | --- | --- |
| 1 | which direction uniformity goes | dao boundary | ✅ **dao boundary** |
| 2 | release level | major | ⚖️ **`fix`** |
| 3 | one change or several | one | ✅ **one change** |
| 4 | where the pg type parsers live | a readme paragraph | ➕ **codegen them** — raised by the wisher |
| 5 | wait for compile-time enforcement (`sql-code-generator#95`)? | no | ✅ **no** |

**#2 — `fix`.** the values that change were already wrong: a dao that declares `id: number` and
returns a string makes no promise a consumer may rely on. the change arrives only when a consumer
regenerates. the cost, on record: a consumer without the pg parsers who coded **against the defect**
finds that code broken by a patch bump. that population is small.

**#3 — one change.** the work splits into A (truthful types), B (the casts), C (the proof). A alone
delivers a *more honest lie* — correct types over values that still diverge, which invites a strict
schema the runtime cannot satisfy. C exists to prove B.

**#5 — drive on.** the rework is clean, so best-guess and drive (`rule.always.defer-fulcrums-to-last`):

1. **#95 does not remove the need for the cast.** perfect types would say the nested `created_at` is
   a `string`; the domain declares `Date`, so a conversion is still owed
2. **#95 is unowned and untimed**, and no downstream is blocked on this route
3. **ship-B-only was rejected** — it knowingly leaves a falsehood in generated code

when #95 lands, the `...Jsoned` shape is **kept as an alias**, not deleted: it is exported from each
dao's `castFromDatabaseObject.ts`, a file consumers import from, so a removal breaks a site that
looks hand-written.

### [answered] does `svc-notifications` install the pg parsers? — two of three

`getDatabaseConnection.ts:8-9` installs oids 20 and 1700, not 1016. so the raw `id` there is already
a `number`, and the `id` half of the reported divergence does not exist in that repo. what broke is
the `timestamptz` half: `Agent.createdAt` is a `Date` raw and a string inside json.

that repo has since landed its own oid-114 reviver and is green, so **no downstream is blocked** and
no urgency argument shapes this scope. the precise limit: no `setTypeParser` on the timestamptz oid
reaches the nested value; a reviver on the outer json oid can.

### [research → executed] does postgres' iso-8601 inside `json_build_object` round-trip through `new Date`?

yes. `generate.integration.test.ts` reads one live row through both paths and asserts `getTime()`
equal.

## research

### external — node-postgres, read from the installed `pg-types@2.2.0`

| oid | type | parser | javascript value |
| --- | --- | --- | --- |
| 20 | `int8` / `bigint` / `bigserial` | `parseBigInteger` | **`string`** |
| 1184 | `timestamptz` | `parseDate` | **`Date`** |
| 1700 | `numeric` | **none registered** | **`string`** |
| 114 / 3802 | `json` / `jsonb` | `JSON.parse` | plain js values |
| 2951 | `uuid[]` | `parseStringArray` | `string[]` |
| 1185 | `timestamptz[]` | `parseDateArray` | `Date[]` |
| 1016 | `int8[]` | `parseBigIntegerArray` | `string[]` |

inside json, postgres renders a `timestamptz` as an iso-8601 string and a `bigint` / `numeric` as a
json number — lossy past `2^53` after `JSON.parse`.

### internal

**three serialization sites, one function** —
`defineQuerySelectExpressionForSqlSchemaProperty.ts`: the raw column, the solo `json_build_object`,
and the array `json_agg(json_build_object(...))` wrapped in `COALESCE(..., '[]'::json)`. all feed one
hydrated view, so one view carries both — e.g. `view_invoice_hydrated.sql` selects `invoice.id` raw
**and** `json_build_object('id', price.id, ...)`. `upsert.ts` selects `dgv.id` raw, a third site.
`findBy*` share the hydrated view; `findByRef` dispatches to `findByUuid` / `findByUnique`.

**the columns** — `defineSqlSchemaGeneratorCodeForProperty.ts` maps `DATE -> TIMESTAMPTZ` and
`NUMBER -> NUMERIC`, so every domain `Date` and `number` lands on a divergence-prone column.

**the untruth is generated here, not upstream.** `sql-code-generator` types what it cannot type
honestly: `SqlFunctionJsonBuildObjectOutput = Record<string, any> | null`, applied to solo and
`json_agg` columns alike. this repo then asserted the raw-row type onto that bag. no
`sql-code-generator` change is required to satisfy the acceptance.

**only a nested literal diverges** — and the reason is a law, not generator policy: an entity is
mutable, so a nested copy could never know whether it is current; a literal's copy is exact forever
(`term=reference`). that makes the narrow blast radius stable.

| method | applies to | selects | diverges? |
| --- | --- | --- | --- |
| `DIRECT_BY_NESTING` | a nested **literal** | `json_build_object` / `json_agg` | **yes** |
| `DIRECT_BY_DECLARATION` | an entity by `Ref<typeof X>` | `.uuid` `varchar` | no |
| `IMPLICIT_BY_UUID` | an entity by `xUuid` | `.uuid` `varchar` | no |

`svc-notifications`' `Agent extends DomainLiteral` and declares `createdAt?: Date` and `id?: number` —
exactly this shape.

**one cast, three callers** — `priceDao/castFromDatabaseObject.ts`:

| caller | how `price` is selected | `price.amount` (numeric) arrives as |
| --- | --- | --- |
| `priceDao/findById.ts` | raw column | `string` by default, `number` under the pg parser |
| `invoiceDao` → `total_price` | solo `json_build_object` | `number` |
| `invoiceDao` → `items[].price` | `json_build_object` inside `json_agg` | `number` |

the third row proves the 2+-levels edgecase: each level casts its own values.

**the fixture** — nested json selects only **user-declared** properties
(`isAUserDefinedDomainObjectProperty`), so `created_at` reaches the blob only when the domain declares
it. `Geocode` (a literal, nested on the train view) now declares `createdAt?: Date`, which puts the
DATE half of the defect on both the raw and the nested path. the NUMBER half (`latitude`, `id`) was
live before it.

**arrays cannot round-trip end-to-end.** `sql-schema-generator`'s `ARRAY_OF` rejects native
primitive arrays, so `Date[]` / `number[]` are proven at the unit and codegen layer only.

## what is awkward

- **the wire stays mixed.** "one runtime type" is met at the dao boundary, not the socket — the gap
  the wisher settled with it in view
- **a boundary conversion sits close to coercion.** what parts them: coercion absorbs a divergence
  downstream, silently, in the domain model; this converts at-cause, loudly, at the persistence
  boundary. a cast that swallowed a bad value would be the smell it exists to remove
- **`id` as a guarded `number` is a compromise.** the truly safe type is a string; every consumer's
  `id?: number` is why we cannot have it
- **the cast still carries an `as`.** it is now a true assertion; to remove it needs upstream #95
