# handoff → sql-schema-generator: native primitive + enum array columns

## .from / .to

- from: `ehmpathy/sql-dao-generator` (wish: consume-primitive-array-classification)
- to: `ehmpathy/sql-schema-generator`
- relationship: `sql-dao-generator` generates schema declarations that `sql-schema-generator`
  then reads to emit postgres DDL. this is a downstream contract gap: the DAO generator now
  emits a declaration shape the schema generator cannot yet consume.

## .what i need (one sentence)

teach `sql-schema-generator` to accept `prop.ARRAY_OF(<primitive>)` and `prop.ARRAY_OF(prop.ENUM([...]))`
and emit a **native postgres array column** (`text[]`, `numeric[]`, `boolean[]`, `timestamptz[]`,
`<enum>[]`) — not a join table.

## .why

`sql-dao-generator` learned to classify the three array kinds and emit the right `prop.*` per kind:

| domain type | sql-dao-generator now emits |
| --- | --- |
| `tags: string[]` | `prop.ARRAY_OF(prop.VARCHAR())` |
| `readings: number[]` | `prop.ARRAY_OF(prop.NUMERIC())` |
| `flags: boolean[]` | `prop.ARRAY_OF(prop.BOOLEAN())` |
| `momentsAt: Date[]` | `prop.ARRAY_OF(prop.TIMESTAMPTZ())` |
| `statuses: Status[]` | `prop.ARRAY_OF(prop.ENUM(['ACTIVE', 'PAUSED']))` |
| `zones: ZoneRef[]` | `prop.ARRAY_OF(prop.REFERENCES(zone))` (unchanged — relation) |
| `photoUuids: string[]` | `prop.ARRAY_OF(prop.UUID())` (unchanged) |

this emission is complete, unit-proven, and green in `sql-dao-generator`. but the emitted schema
declaration is INERT downstream, because `sql-schema-generator@0.25.3` throws on every non-reference,
non-uuid element.

## .the current blocker (verified in source)

`sql-schema-generator/src/domain.operations/define/defineProperty.ts:367` (same at published 0.25.3
and at HEAD):

```ts
export const ARRAY_OF = (property: Property) => {
  const isArrayOfReferences = !!property.references;
  const isArrayOfUuids = serialize(property) === serialize(UUID());
  if (!isArrayOfReferences && !isArrayOfUuids)
    throw new Error('only arrays of REFERENCEs or UUIDs are supported');
  return new Property({ ...property, array: true });
};
```

two facts this reveals:

1. **`ARRAY_OF` accepts only `REFERENCES(...)` or `UUID()`.** `VARCHAR/NUMERIC/BOOLEAN/TIMESTAMPTZ/ENUM`
   all fail both checks and throw. this is the exact error a consumer hits:
   `Error: only arrays of REFERENCEs or UUIDs are supported`.
2. **even the cases that pass do NOT emit a native array column.** the `array: true` flag drives a
   **join table** (its doc comment describes a child map-table plus a BINARY(32) column).
   proof — a `_uuids` array today generates a child table, not a `uuid[]` column:

   ```sql
   -- sql-dao-generator exampleProject, generated by sql-schema-generator:
   CREATE TABLE train_engineer_version_to_license_uuid (
     id bigserial NOT NULL,
     train_engineer_version_id bigint NOT NULL,
     license_uuid uuid NOT NULL,
     array_order_index smallint NOT NULL,
     ...
   );
   ```

so there is no native-array path anywhere in the current schema generator — the whole array model
is join-table-based. what the wish wants (`tags text[]` on the base row) is a new capability.

## .the contract i need

### 1. `ARRAY_OF` accepts primitive + enum element props

extend `ARRAY_OF` to accept these element props (in addition to the current `REFERENCES` / `UUID`):
`VARCHAR`, `NUMERIC`, `BOOLEAN`, `TIMESTAMPTZ`, `ENUM([...])`. (matches the solo-primitive prop set;
the exact element→pg-type map is below.)

### 2. primitive/enum arrays → native array column on the base table

a primitive or enum array prop must produce a single native postgres array column on the base
(and version, if updatable) table — NOT a join table:

| element prop | native column type |
| --- | --- |
| `VARCHAR()` | `text[]` (or `varchar[]`) |
| `NUMERIC()` | `numeric[]` |
| `BOOLEAN()` | `boolean[]` |
| `TIMESTAMPTZ()` | `timestamptz[]` |
| `ENUM([...])` | `<enum_type>[]` (native enum array; reuse the enum type the solo `ENUM` path defines) |

reference arrays (`ARRAY_OF(REFERENCES(...))`) and, for backward-compat, uuid arrays
(`ARRAY_OF(UUID())`) keep their current join-table behavior — this change is additive and must not
regress them.

### 3. round-trip through the generated machinery

the native array column must flow through the pieces a consumer relies on end-to-end:

- **DDL**: `CREATE TABLE ... (tags text[], ...)` on the base table (and version table when the prop
  is updatable).
- **upsert function** (`upsert_*.sql`): accept the array as a single argument and write it to the
  column (no per-element child-row insert).
- **hydrated view**: select the array column straight through (no `array_agg` join collapse needed
  for the native-array case).
- **uniqueness / CVP**: the current-version-pointer + change-detection machinery must treat the
  array column as a normal scalar-ish column for value comparison (postgres array equality), so an
  unchanged array does not spuriously bump the version.

## .open question for you — native array vs join-table array (we can go either way)

before you build native arrays, we want your read on whether native arrays are actually the right
storage, or whether the join-table model you already have is better kept.

the key enabler: the generated **hydrated view** abstracts the storage away. whether `tags` lives as
a native `text[]` column or as a `sensor_version_to_tag` child table collapsed via `array_agg(...
order by array_order_index)`, the view can present an identical `text[]` shape to the DAO. so the
DAO layer (our repo) does not care which you pick — the view closes the difference. that makes this
a two-way door, and we would rather pick on merits than by default.

what we would like your judgment on:

| dimension | native `text[]` column | join-table array (current model) |
| --- | --- | --- |
| read (small list) | single row, no join | view does `array_agg` join |
| element-level mutation | whole-value rewrite | per-row insert/delete |
| element-level FK / uniqueness | none | natural (per element) |
| membership query (`x = ANY(...)`) | needs GIN index | standard index on child |
| array size / bloat | postgres row-size limits | unbounded |
| ordering | native | via `array_order_index` |
| generator machinery | new column path | already built |

concrete questions:

1. is there a downside to native arrays that the join-table model avoids and that would bite a
   consumer later (bloat, mutation cost, index limits, migration pain)?
2. since the view can present either as `text[]`, would you rather:
   (a) emit native array columns for primitive/enum arrays (what this handoff specs), or
   (b) keep the join-table storage and only widen it to primitive/enum element types (so the
       `_to_*` child table holds `text`/`numeric`/enum instead of only uuid/reference), and let the
       view collapse it to `text[]` — giving the DAO the same shape with no new storage concept?
3. or (c) support both and make it a per-prop knob (e.g. `ARRAY_OF(..., { storage: 'native' | 'relation' })`)?

our default preference is native arrays (the wisher settled on that for small, read-mostly
primitive lists), but if you see a real hazard, (b) with the view as the seam is equally acceptable
to us — the DAO output is identical either way. tell us which you would rather own.

## .acceptance (what proves it done)

a schema declaration like:

```ts
export const sensor: Entity = new Entity({
  name: 'sensor',
  properties: {
    serialNumber: prop.VARCHAR(),
    tags: { ...prop.ARRAY_OF(prop.VARCHAR()), updatable: true },
    readings: { ...prop.ARRAY_OF(prop.NUMERIC()), updatable: true },
    statuses: { ...prop.ARRAY_OF(prop.ENUM(['ACTIVE', 'FAULTED', 'OFFLINE'])), updatable: true },
  },
  unique: ['serialNumber'],
});
```

should (storage per the open question above — native column OR view-collapsed join table; the
DAO-visible contract is identical either way):

1. accept the declaration without throwing (the `ARRAY_OF(<primitive>)` / `ARRAY_OF(ENUM)` block is lifted).
2. apply cleanly to a real postgres (via `sql-schema-control apply`).
3. the hydrated view presents each as its element array (`text[]` / `numeric[]` / `boolean[]` /
   `timestamptz[]` / `<enum>[]`) — this is the shape our generated DAO cast reads.
4. round-trip: upsert `{ tags: ['a','b'], readings: [1,2], statuses: ['ACTIVE'] }`, read it back
   equal; re-upsert the same values → no version bump; upsert changed values → one new version.

(if you pick native columns per the open question, #3 is a straight column select and the base/version
tables carry `text[]` etc.; if you pick the view-collapsed join table, #3 is an `array_agg` in the
view. our DAO does not distinguish.)

once this ships (published version bumped), `sql-dao-generator` un-defers its own e2e step: add a
`Sensor` fixture with these three array kinds to `exampleProject`, regenerate, and add the live
round-trip test. this is already scoped and understood on our side — the ONLY blocker is this
downstream capability.

## .scope notes

- decision already settled with the wisher: native array columns, NOT a serialized `TEXT`/json
  column, and NOT a join table. the join-table path is correct for reference arrays (element-level
  FKs), but wrong for small read-mostly primitive/enum lists — which is the case this serves.
- upstream twin: this mirrors the `domain-objects-metadata` #24 dependency the same wish already
  consumed (guard family that classifies the three array kinds). that half shipped (v0.7.9+); this
  is the second, still-open half.
