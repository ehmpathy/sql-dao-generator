# handoff → sql-schema-generator: native primitive + enum array columns

## .from / .to

- from: `ehmpathy/sql-dao-generator` (wish: consume-primitive-array-classification)
- to: `ehmpathy/sql-schema-generator`
- the gap: sql-dao-generator now generates a schema declaration shape that sql-schema-generator
  cannot consume

## .the ask

accept `prop.ARRAY_OF(<primitive>)` and `prop.ARRAY_OF(prop.ENUM([...]))`, and present each as its
element array (`text[]`, `numeric[]`, `boolean[]`, `timestamptz[]`, `<enum>[]`).

## .why

sql-dao-generator classifies the three array kinds and generates:

| domain type | generated prop |
| --- | --- |
| `tags: string[]` | `prop.ARRAY_OF(prop.VARCHAR())` |
| `readings: number[]` | `prop.ARRAY_OF(prop.NUMERIC())` |
| `flags: boolean[]` | `prop.ARRAY_OF(prop.BOOLEAN())` |
| `momentsAt: Date[]` | `prop.ARRAY_OF(prop.TIMESTAMPTZ())` |
| `statuses: Status[]` | `prop.ARRAY_OF(prop.ENUM(['ACTIVE', 'PAUSED']))` |
| `zones: ZoneRef[]` | `prop.ARRAY_OF(prop.REFERENCES(zone))` (unchanged) |
| `photoUuids: string[]` | `prop.ARRAY_OF(prop.UUID())` (unchanged) |

unit-proven here, and inert downstream.

## .the blocker (verified in source)

`sql-schema-generator/src/domain.operations/define/defineProperty.ts:367` (0.25.3 and HEAD):

```ts
export const ARRAY_OF = (property: Property) => {
  const isArrayOfReferences = !!property.references;
  const isArrayOfUuids = serialize(property) === serialize(UUID());
  if (!isArrayOfReferences && !isArrayOfUuids)
    throw new Error('only arrays of REFERENCEs or UUIDs are supported');
  return new Property({ ...property, array: true });
};
```

1. primitive and enum elements fail both checks and throw
2. the cases that pass produce a **join table**, not a native column:

```sql
-- sql-dao-generator exampleProject, generated by sql-schema-generator
CREATE TABLE train_engineer_version_to_license_uuid (
  id bigserial NOT NULL,
  train_engineer_version_id bigint NOT NULL,
  license_uuid uuid NOT NULL,
  array_order_index smallint NOT NULL,
  ...
);
```

⇒ no native-array path exists today. this is a new capability.

## .the contract

1. `ARRAY_OF` accepts `VARCHAR`, `NUMERIC`, `BOOLEAN`, `TIMESTAMPTZ`, `ENUM([...])`
2. each presents through the hydrated view as its element array:

| element prop | presented as |
| --- | --- |
| `VARCHAR()` | `text[]` (or `varchar[]`) |
| `NUMERIC()` | `numeric[]` |
| `BOOLEAN()` | `boolean[]` |
| `TIMESTAMPTZ()` | `timestamptz[]` |
| `ENUM([...])` | `<enum_type>[]`, the type the solo `ENUM` path defines |

3. reference and uuid arrays keep their join-table behavior — additive, no regression
4. the pieces a consumer relies on all carry it: DDL, the `upsert_*.sql` function, the hydrated
   view, and change detection — an unchanged array must not bump the version

## .open question — native column or join table

our preference is native columns (the wisher settled on them for small, read-mostly primitive
lists). but the hydrated view hides storage: a native `text[]` and a child table collapsed by
`array_agg(... order by array_order_index)` present the same shape. so the dao does not care, and
this is a two-way door.

| dimension | native `text[]` | join table (current model) |
| --- | --- | --- |
| read (small list) | one row, no join | `array_agg` join in the view |
| element mutation | whole-value rewrite | per-row insert/delete |
| element FK / uniqueness | none | natural |
| membership query (`x = ANY(...)`) | needs a GIN index | standard index on child |
| size | row-size limits | unbounded |
| generator machinery | new column path | already built |

questions:
1. does a native array carry a hazard the join table avoids — bloat, mutation cost, index limits,
   migration pain?
2. would you rather (a) add native columns, (b) widen the join table to primitive/enum elements and
   let the view collapse them, or (c) support both via a per-prop knob
   (`ARRAY_OF(..., { storage: 'native' | 'relation' })`)?

## .acceptance

```ts
export const sensor: Entity = new Entity({
  name: 'sensor',
  properties: {
    serialNumber: prop.VARCHAR(),
    tags: { ...prop.ARRAY_OF(prop.VARCHAR()), updatable: true },
    readings: { ...prop.ARRAY_OF(prop.NUMERIC()), updatable: true },
    statuses: { ...prop.ARRAY_OF(prop.ENUM(['ACTIVE', 'FAULTED', 'OFFLINE'])), updatable: true },
  },
  unique: ['serialNumber'],
});
```

1. the declaration is accepted
2. it applies cleanly to real postgres via `sql-schema-control apply`
3. the hydrated view presents each as its element array
4. round-trip: upsert `{ tags: ['a','b'], readings: [1,2], statuses: ['ACTIVE'] }` reads back equal;
   the same values again → no version bump; changed values → one new version
