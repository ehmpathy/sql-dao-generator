# vision: sql-dao-generator — consume primitive-array + enum-array classification

## tl;dr

`sql-dao-generator` learns to tell three kinds of array apart and emit the right postgres
column for each:

- **primitive array** (`string[]`, `number[]`, `boolean[]`, `Date[]`) → a native array column
  (`prop.ARRAY_OF(prop.VARCHAR())`, `prop.ARRAY_OF(prop.NUMERIC())`, …)
- **enum array** (`Status[]`) → a native enum array column (`prop.ARRAY_OF(prop.ENUM([...]))`)
- **domain-object-reference array** (`ItemRef[]`) → a relation (foreign keys), unchanged

it classifies via the `domain-objects-metadata` guard family
(`isPrimitiveArrayProperty` / `isEnumArrayProperty` / `isReferenceArrayProperty`), which read
the array's element type. today the generator has a single array branch that treats every array
as a domain-object array and throws for every other case — so a `string[]` is rejected.

---

## the outcome world

### day-in-the-life

a teammate models a domain object with precise array types:

```ts
export interface Provider {
  slug: string;
  tags: string[];             // primitive array
  scores: number[];           // primitive array
  statuses: ProviderStatus[]; // enum array  (type ProviderStatus = 'ACTIVE' | 'PAUSED')
  zones: ServiceZoneRef[];    // domain-object-reference array
  photo_uuids: string[];      // implicit by-uuid reference array
}
```

they run dao codegen. every array kind maps to the right column:

| property | emitted column |
| --- | --- |
| `tags: string[]` | `prop.ARRAY_OF(prop.VARCHAR())` → `text[]` |
| `scores: number[]` | `prop.ARRAY_OF(prop.NUMERIC())` → `numeric[]` |
| `statuses: ProviderStatus[]` | `prop.ARRAY_OF(prop.ENUM([...]))` → native `enum[]` |
| `zones: ServiceZoneRef[]` | relation / foreign keys |
| `photo_uuids: string[]` | `prop.ARRAY_OF(prop.UUID())` |

### before / after

| aspect | before | after |
| --- | --- | --- |
| `tags: string[]` | throws `UserInputError` | native `text[]` column |
| `scores: number[]` | throws `UserInputError` | native `numeric[]` column |
| `statuses: Status[]` | throws `UserInputError` | native `enum[]` column |
| `zones: ZoneRef[]` | relation | relation (unchanged) |
| `photo_uuids: string[]` | `prop.ARRAY_OF(prop.UUID())` | `prop.ARRAY_OF(prop.UUID())` (unchanged) |
| a consumer's domain type | downgraded (`tags: string; // todo: revert`) | modeled truthfully as `string[]` |

### the "aha"

the array's element type already carries the answer — `property.of.type`:

- `REFERENCE` → domain-object array → relation
- `ENUM` → enum array → native `enum[]`
- `STRING | NUMBER | BOOLEAN | DATE` → primitive array → native `<primitive>[]`

the generator has thrown that signal away because its single array branch collapsed all kinds
into "array of domain objects." the fix is to branch on what the metadata already knows.

## user experience

### who is the user?

two users: the **human who runs dao codegen** in a consumer service
(`<consumer> npm run generate:dao:postgres`), and the **generated DAO code** their app then
runs. the contract is: domain-object types in → migration-ready schema + typed DAO out.

### usecase

> "i model a domain object with `tags: string[]`, `statuses: Status[]`, `zones: ZoneRef[]`.
> generate a postgres DAO that stores each array with the right column type, without a downgrade
> of my domain types."

### contract inputs & outputs

- **input**: hydrated `DomainObjectMetadata` — what `introspect` returns; the generator already
  consumes this via `extractDomainObjectMetadatasFromConfigCriteria` → `introspect(searchPaths)`.
- **output**: the emitted `prop.*` expression per property in the generated schema entity, plus
  the matched cast + find-by code in the generated DAO.

the property-level branch reads (element → prop):

```ts
// reference array → relation (prior behavior)
if (isReferenceArrayProperty(domainObjectProperty)) { /* prior relation logic */ }

// enum array → native enum[] column
if (isEnumArrayProperty(domainObjectProperty))
  return `prop.ARRAY_OF(prop.ENUM([${options.map((o) => `'${o}'`).join(', ')}]))`;

// primitive array → native <primitive>[] column
if (isPrimitiveArrayProperty(domainObjectProperty))
  return `prop.ARRAY_OF(prop.${propForPrimitive(domainObjectProperty.of.type)}())`;
```

where `propForPrimitive` mirrors the extant solo-primitive map: `STRING→VARCHAR`,
`NUMBER→NUMERIC`, `BOOLEAN→BOOLEAN`, `DATE→TIMESTAMPTZ`.

### timeline

1. `introspect` (metadata) → `{ type: ARRAY, of: { type: STRING } }` — already correct.
2. `defineSqlSchemaGeneratorCodeForProperty` → branches on the three array kinds.
3. `defineDao*` → cast + find-by that agree with the emitted column.
4. consumer runs codegen → precise domain types, no downgrade.

## mental model

- to a friend: *"arrays of plain values like `string[]` now get their own native postgres array
  column instead of a mistaken identity as a table of linked records."*
- analogy: a `string[]` is a **bag of values carried inside the row** (`text[]`); a `ZoneRef[]`
  is a **set of links to other rows** (foreign keys / join). the metadata always knew which was
  which; the generator now honors that.

| they say (consumer dev) | we say (this repo) |
| --- | --- |
| "a text/number array column" | primitive-array property (`of.type` is a primitive) |
| "an enum array column" | enum-array property (`of.type === ENUM`) |
| "linked records / a join" | reference-array property (`of.type === REFERENCE`) |

## the guard family we consume

`domain-objects-metadata` exposes a three-way classifier, each derived from a single
`getArrayElementKind` — so the three kinds are mutually exclusive by construction:

| guard | true when element `of.type` is | routes to |
| --- | --- | --- |
| `isReferenceArrayProperty` | `REFERENCE` | relation |
| `isEnumArrayProperty` | `ENUM` | native `enum[]` |
| `isPrimitiveArrayProperty` | `STRING \| NUMBER \| BOOLEAN \| DATE` | native `<primitive>[]` |

a companion `isReferenceProperty` guards a solo (non-array) domain-object reference.

all four operate on **hydrated** metadata; `introspect` returns hydrated metadata, so an enum
array's element is `ENUM` (not `REFERENCE`) by the time this repo sees it.

### the rename this implies

this repo currently imports two older guard names that the metadata package no longer exposes:

- `isDomainObjectArrayProperty` → replaced by `isReferenceArrayProperty`
- `isDomainObjectReferenceProperty` → replaced by `isReferenceProperty`

both old names appear across the codebase (5 files). the change is a rename sweep **plus** a
semantic split at the two sites that used the old array guard as a stand-in for "is any array"
(the `_uuids` sites — see the audit below): those must move to `isPrimitiveArrayProperty`, not
`isReferenceArrayProperty`.

## the property-branch audit

`isDomainObjectArrayProperty` appears at 6 call expressions across 5 files. two files are
**mixed** — a call to replace with `isReferenceArrayProperty` AND a call to repair toward
`isPrimitiveArrayProperty` sit in the same file, so the audit is per-call-expression, not
per-file:

| # | file:line | new target | kind |
| - | --- | --- | --- |
| 1 | `sqlSchemaGenerator/defineSqlSchemaGeneratorCodeForProperty.ts:33` | split → 3 branches | **primary rewrite** |
| 2 | `sqlSchemaRelationship/defineSqlSchemaReferenceForDomainObjectProperty.ts:112` | `isReferenceArrayProperty` | pure rename |
| 3 | `sqlSchemaRelationship/defineSqlSchemaReferenceForDomainObjectProperty.ts:121` | `isPrimitiveArrayProperty` | **repair — `_uuids`** (⚠️ mixed file, with #2) |
| 4 | `sqlSchemaRelationship/isADirectlyNestedDomainObjectProperty.ts:25` | `isReferenceArrayProperty` | pure rename |
| 5 | `databaseAccessObjects/defineDaoUtilCastMethodCodeForDomainObject.ts:31` | `isReferenceArrayProperty` | pure rename |
| 6 | `databaseAccessObjects/defineDaoUtilCastMethodCodeForDomainObject.ts:83` | `isPrimitiveArrayProperty` | **repair — `_uuids`** (⚠️ mixed file, with #5) |
| 7 | `databaseAccessObjects/defineDaoFindByMethodCodeForDomainObject.ts:104` | `isReferenceArrayProperty` | pure rename |

plus every `isDomainObjectReferenceProperty` call renames to `isReferenceProperty`.

- **pure renames (#2, #4, #5, #7)** conjoin `&& isDomainObjectReferenceProperty(x.of)`, which
  the new guard already implies at the element level — behaviorally inert, but rename both the
  array guard and the inner reference guard.
- **repairs (#3, #6)** used the old array guard to detect a `_uuids` string array. that is a
  primitive array, so they move to `isPrimitiveArrayProperty`; a rename to
  `isReferenceArrayProperty` there would silently drop the `_uuids` behavior.
- the primary site (#1) also holds the `_uuids` emission inside its array block, so the `_uuids`
  case must live in the primitive branch after the split — a third place the `_uuids` behavior
  must survive.

## evaluation

### how well it solves the goal

- `tags: string[]` + `scores: number[]` → native array columns, no `UserInputError`.
- `Status[]` (enum) → native `enum[]`, distinct from primitive arrays.
- `ZoneRef[]` (reference) → relation, no regression.
- `_uuids` special case preserved across all three of its sites.

### pros

- honest column types — `text[]` / `numeric[]` / `enum[]` are queryable, indexable, and typed at
  the db, and reuse the `prop.ARRAY_OF(prop.<primitive>())` pattern the `_uuids` case already
  proves.
- each guard means what its name says; the three kinds are mutually exclusive, so branch order is
  safe.
- the `isEnumArrayProperty` guard removes the need for a hand-rolled `of.type === ENUM` probe.

### cons / tradeoffs

- **three array kinds, not two** — a reader now follows a three-way branch. acceptable for the
  column-type precision it buys.
- **native arrays carry the usual array tradeoffs** — no element-level foreign keys, whole-value
  rewrite on mutation, membership queries need a GIN index. these are correct for small,
  read-mostly primitive lists (the case this branch serves) and are why reference arrays still go
  to relations. a consumer whose primitive list is large, heavily element-mutated, or queried by
  membership should hand-model a child table instead — the escape hatch the `UserInputError` used
  to prescribe.

### edgecases & pit-of-success

| edgecase | intended behavior |
| --- | --- |
| `tags?: string[]` / `string[] \| null` | outer `nullable`/`required` preserved on the array column; element stays primitive |
| `photo_uuids: string[]` (matches a dobj) | implicit by-uuid relation (unchanged) |
| `favorite_fruit_uuids: string[]` (no matched dobj) | `prop.ARRAY_OF(prop.UUID())` (unchanged) |
| `Variant[]` where `type Variant = 'A' \| 'B'` | element hydrates to STRING ⇒ primitive array ⇒ `text[]` |
| `Status[]` where `Status` is an enum | element `of.type === ENUM` ⇒ native `enum[]` (not `text[]`) |
| `ZoneRef[]` (domain-object reference) | relation (unchanged) |
| nested / 2D array (`string[][]`) | element `of.type === ARRAY` matches no guard ⇒ **fails loud** with a clear "unsupported array shape" error (no silent mis-emit; unsupported, as today) |
| primitive array in a **unique key** | find-by type inference assumes ARRAY ⇒ reference and would deref a null reference; must **fail loud**, not silently mis-emit. support for arrays-in-unique-keys is out of scope |

## decisions & open questions

### decisions (settled with the wisher)

1. **column type = native `<primitive>[]`.** primitive arrays emit
   `prop.ARRAY_OF(prop.<primitive>())` (`text[]`, `numeric[]`, `boolean[]`, `timestamptz[]`), not
   a serialized `TEXT`/json column — native arrays stay queryable and typed, and no `prop.JSON()`
   exists in the schema-generator vocabulary.
2. **`boolean[]` / `Date[]` — test-covered.** support for them arrives free via
   `isPrimitiveArrayProperty` (its element set includes BOOLEAN and DATE), so acceptance covers
   them with data-driven cases (`boolean[]` → `prop.ARRAY_OF(prop.BOOLEAN())`, `Date[]` →
   `prop.ARRAY_OF(prop.TIMESTAMPTZ())`) to lock the behavior against silent regression.
3. **`Date[]` element map = `TIMESTAMPTZ`.** inherits the extant solo `DATE → TIMESTAMPTZ` map.
4. **primitive array in a unique key = fail loud.** a silent mis-emit is unacceptable; support is
   out of scope unless later requested.
5. **nested arrays (`string[][]`) = fail loud.** they match no guard and stay unsupported, but
   the error message narrows from "only domain-object arrays" to "unsupported array shape."

### open questions

- none block. external research: none — pure codegen against local ehmpathy packages.

## groundwork

### external research

none — no external services or APIs. this is typescript codegen against local ehmpathy packages.

### internal research (verified)

**the metadata guard family (consumed contract)** — `domain-objects-metadata`:
- `src/index.ts` exports `isPrimitiveArrayProperty`, `isReferenceArrayProperty`,
  `isEnumArrayProperty`, `isReferenceProperty`, `introspect`.
- `isPrimitiveArrayProperty` → element `of.type ∈ {STRING, NUMBER, BOOLEAN, DATE}`.
- `isReferenceArrayProperty` → element `of.type === REFERENCE`.
- `isEnumArrayProperty` → element `of.type === ENUM`.
- all three derive from `getArrayElementKind` and note "operates on hydrated metadata."

**this repo consumes hydrated metadata** —
`src/domain.operations/config/getConfig/extractDomainObjectMetadatasFromConfigCriteria.ts:15`
calls `introspect(searchPaths)` and feeds the result to the generate pipeline.

**the primary array branch (the throw)** —
`src/domain.operations/define/sqlSchemaGenerator/defineSqlSchemaGeneratorCodeForProperty.ts:33-65`:
reference-array → relation, `_uuids` string[] → `prop.ARRAY_OF(prop.UUID())`, else `UserInputError`.
this is the branch to split into three.

**solo-primitive → prop map (mirror for the element type)** — same file `:78-89`:
`STRING→VARCHAR`, `NUMBER→NUMERIC`, `BOOLEAN→BOOLEAN`, `DATE→TIMESTAMPTZ`, `ENUM→ENUM([...])`.

**the emission target — native arrays, no json prop** — `ehmpathy/sql-schema-generator`
`src/domain.operations/define/defineProperty.ts` exports `VARCHAR, NUMERIC, BOOLEAN, TIMESTAMPTZ,
ENUM, ARRAY_OF, UUID` (and more), but no `JSON`/`JSONB`. `ARRAY_OF(prop.UUID())` already ships
(test assets + integration tests), which proves `ARRAY_OF` wraps a primitive prop into a native
postgres array.

**the six old-guard call sites** — `grep isDomainObjectArrayProperty src/` →
`defineSqlSchemaGeneratorCodeForProperty.ts:33`, `defineSqlSchemaReferenceForDomainObjectProperty.ts:112,121`,
`isADirectlyNestedDomainObjectProperty.ts:25`, `defineDaoUtilCastMethodCodeForDomainObject.ts:31,83`,
`defineDaoFindByMethodCodeForDomainObject.ts:104`; every `isDomainObjectReferenceProperty` call
renames alongside.

**the acceptance test layer** — array emission is proven at the unit layer by exact-string
`toEqual` in `defineSqlSchemaGeneratorCodeForProperty.test.ts` (e.g. `:226-227`
`prop.ARRAY_OF(prop.REFERENCES(planeExternalId))`, `:311-312` nullable variant), plus file-level
snapshots (`__snapshots__/`) and integration on generated files
(`defineSqlSchemaGeneratorCodeFilesForDomainObjects.integration.test.ts`). mirror those cases with
`ARRAY_OF(VARCHAR)` / `ARRAY_OF(NUMERIC)` / `ARRAY_OF(BOOLEAN)` / `ARRAY_OF(TIMESTAMPTZ)` /
`ARRAY_OF(ENUM([...]))` and a nested-array throw case.

## what is awkward

- **the `UserInputError` best-practice message goes partly stale.** its stance — "persisted
  domain objects should only have arrays of other domain objects" — no longer holds for primitive
  and enum arrays. the message narrows to guidance for the genuinely unsupported shapes (nested
  arrays, unknown element types), rather than a blanket rule the branch no longer enforces.
- **the deliverable spans the whole generated DAO, not one function.** a primitive array flows
  through the schema property, the cast method, and find-by type inference; all three must compile
  and round-trip it. the property branch is the headline, but the DAO-wide coherence is the real
  acceptance bar.
- **two mixed files.** the reference-guard rename and the `_uuids` repair live in the same file
  twice; a per-file verdict is wrong, so the edits are per-call-expression.
