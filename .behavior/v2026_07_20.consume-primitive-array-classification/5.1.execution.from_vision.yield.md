## the shared predicates — one question, one file

| predicate | the question | consumers |
|---|---|---|
| `define/isUuidReferenceArrayProperty.ts` | `_uuids$` suffix **and** a STRING element? | generator, schema-control, relationship — all three |
| `sqlSchemaControl/isNativeArrayColumnProperty.ts` | one native column, no join table? | schema-control only |
| `sqlSchemaRelationship/isNonReferenceArrayColumn.ts` | a non-reference array, at the sql layer? | the unique-key guard |

- the generator does not use `isNativeArrayColumnProperty`: it emits different code per kind, so it
  branches on the base guards
- `isNativeArrayColumnProperty` is order-dependent — reference and `_uuids` arrays are ruled out first
- `isNonReferenceArrayColumn` reads sql metadata, where `.reference` is set for both reference and
  `_uuids` arrays. so it admits `_uuids` in a unique key and rejects every native array — a future
  element kind with `.reference = null` is caught with no edit
- why one `_uuids` predicate: each layer once matched `_uuids` its own way, and they diverged —
  `score_uuids: number[]` got a native `numeric[]` column from the generator and a `_to_score_uuid`
  join table from control, and `imageUuidsAtCapture` (an unanchored `/Uuids/`) read as a reference
  in the relationship layer. both cases are now locked by tests at the shared path

## schema-control

`defineArrayJoinTableRelpath({ sqlSchemaRelationship, propertyRelationship, tableName })` returns the
join-table relpath or `null` for a native array; the base and version loops both call it. the
`_uuids` check precedes the native check, since a `_uuids` array is also a primitive string array.

## errors

`asHelpfulSqlSchemaGeneratorError` returns `ConstraintError` for the native-array limitation
(caller-fixable, exit 2) and `MalfunctionError` for any other stderr (exit 1), raw stderr kept as
metadata. its signal string is a best-effort match — re-verify on the next upstream upgrade; the
fallback still fails loud.

## the downstream gap

a `Sensor` probe (`tags: string[]`, `readings: number[]`, `statuses: SensorStatus[]`) through
`generate` proved this repo's half: the declaration carried `prop.ARRAY_OF(prop.VARCHAR())` etc. the
next step threw:

```
Error: only arrays of REFERENCEs or UUIDs are supported
  at Object.ARRAY_OF (sql-schema-generator@0.25.3/.../defineProperty.ts:371)
```

`ARRAY_OF` accepts only `REFERENCES(...)` or `UUID()`, and even then it builds a join table, never a
native array column. `0.25.3` is the latest published version and HEAD carries the same throw, so no
version supports native primitive or enum arrays. the probe was reverted.

the wisher chose to build the downstream support. `handoff.sql-schema-generator.md` specs the
`ARRAY_OF` lift and asks one two-way-door question — native column vs the extant join table, which
the hydrated view hides from the DAO either way. the sql-schema-generator behavior boots from a
dispatch that points back to it.

⇒ the emitted `prop.ARRAY_OF(prop.<primitive>())` is inert until that lands.
