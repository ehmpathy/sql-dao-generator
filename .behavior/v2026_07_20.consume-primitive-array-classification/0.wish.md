# wish: sql-dao-generator — consume primitive-array + enum-array classification

## .what

update `sql-dao-generator` to branch on the three array kinds instead of the
current throw, so `string[]` / `number[]` become native `<primitive>[]` columns
(`text[]` / `numeric[]`), `enum[]` becomes a native `enum[]` column, and
domain-object arrays stay relations.

## .why

today `sql-dao-generator` rejects `string[]` / `number[]` — the old guard
`isDomainObjectArrayProperty` matched EVERY array, so a primitive array fell
into the domain-object-array branch and threw `UserInputError`. that forced
consumers to downgrade their domain types (`tags: string;  // todo: revert`).

the full spec is the mechanic-authored handoff in the upstream repo — read it
first, it is the source of truth (handoffs-at-source):

- `ehmpathy/domain-objects-metadata` worktree:
  `.behavior/v2026_06_30.fix-extract-primitive-arrays/handoff.sql-dao-generator.md`
- upstream contract: `ehmpathy/domain-objects-metadata#24`
- upstream vision: same behavior dir, `1.vision.yield.md`

## .dependency (important)

this consumes an upstream contract that has NOT shipped yet. the metadata task
(#24) is still at its vision stone; it will ship:
- `isDomainObjectArrayProperty` NARROWED (⚠️ breaks callers — true only for ref arrays)
- `isPrimitiveArrayProperty` ADDED (STRING | NUMBER | BOOLEAN | DATE)
- `enum[]` kept distinct (element `of.type === ENUM`)

the branch logic can be built now against this expected contract, but the
acceptance step (bump domain-objects-metadata to the version that ships the
guards) is BLOCKED until #24 merges. flag that gate rather than fake it.

## .acceptance

  + `isPrimitiveArrayProperty` (gated on #24 — see dependency above)

  native `<primitive>[]` columns (`text[]` / `numeric[]`), no `UserInputError`
- a fixture with an `enum[]` prop generates a native `enum[]` column (NOT a serialized text column)
- domain-object-array props (`Item[]`) still generate relations — no regression
- the narrowed `isDomainObjectArrayProperty` does not break the four callsites above
- the `_uuids`-suffix special case still emits `prop.ARRAY_OF(prop.UUID())`
