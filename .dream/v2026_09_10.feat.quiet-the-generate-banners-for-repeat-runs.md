# 🌙 dream: a `--quiet` flag for the `generate` consumer banners

- kind  = feat
- owner = `ehmpathy/sql-dao-generator`
- caught = 2026-09-10
- status = open

## .the cue that fired
the two consumer banners — `🔌 One opt-in remains:` (parsers) and `📦 One dependency is required:`
(`helpful-errors`) — print on every `generate` run, a byte-identical no-op among them. a consumer
who generates in CI on each commit reads the same two blocks every time.

## .the gap, precisely
two repairs suggest themselves, and both fail:

| the proposal | why it fails |
| --- | --- |
| suppress once the consumer wired the opt-in | undetectable — `setDbTypeParsers()` sits in the consumer's own connection file |
| suppress on a no-op run | the opt-in fails silently, so the prompt would vanish when a new engineer re-runs |
| **an explicit `--quiet`** | the consumer states the intent; the tool infers naught |

⇒ both suppressions also make stdout depend on prior state, so the acceptance snapshot would flake.

## .the shape of the fix
1. `--quiet` boolean in `src/contract/commands/generate.ts`, default `false`
2. thread it into `src/domain.operations/commands/generate.ts`; guard the two banner blocks. the
   `[GENERATED]` lines stay — they report work, the banners state a demand
3. default stays loud. a silent-failure prompt that quiets itself is the defect
4. snapshot both paths in `generate.acceptance.test.ts`, one `[tN]` each
5. `CI=true` should probably NOT imply it — CI is where a silent wrong value ships. record the call

## .why it is not done in this round
SAFE fails: a CLI flag is new public surface, and this route ships at `fix`. a `feat` on a patch
bump teaches consumers the release level means less than it says. CLEAN holds — two files this diff
already opens.
