# 🌙 dream: the generated-fixture freshness guard races the suite that regenerates it

- kind  = fix
- owner = `ehmpathy/sql-dao-generator`
- caught = 2026-09-09
- status = ✅ discharged within the same route

## .how it was discharged
the guards are gone, and the race with them:
- `test:unit` and `test:integration` each run `test:integration:provision-generated-files-to-import`
  with `&&` before their own jest run, so the example project is regenerated from source first
- the suites that grade the generated module (`daoCasts.behavior.test.ts`,
  `defineDaoCastsCodeFile.test.ts`) import a fixture fresh by construction, so a `toEqual` against
  the definer would pass by construction and was deleted

the provision step's own gap is a separate dream:
`v2026_09_17.fix.provision-step-passes-with-no-tests.md`.

## .the gap, as it stood
two unit suites contended on one dir with no jest order guarantee:

| suite | what it did to `exampleProject/src/access/daos/` |
| --- | --- |
| `commands/generate.test.ts` | wrote it, via the real `generate` command |
| the two freshness-guarded suites | read it with `readFileSync` + `toEqual`, and imported it |

- reader first → the guard graded the committed fixture, as designed. it caught one real staleness
  (a widened `DbTypeParserCollisionError` message)
- writer first → it graded a file just written by the same definer, so it could not fail
- 🔴 the imports ran at module load, so when the reader ran first against a stale fixture, the
  behavior tests graded a stale module — the hazard the guard existed to prevent

⇒ `rule.forbid.order-dependence` and `rule.forbid.race-conditions`, with a `failhide` consequence.
