# 🌙 dream: cast json-nested NUMBER values to text in the generated select

- kind  = feat
- owner = `ehmpathy/sql-dao-generator`
- caught = 2026-09-21
- status = open

## .the cue that fired
research into how other projects handle this defect found drizzle-orm hit the identical divergence
(`drizzle-orm#4380` — bigints arrive as ints only through `json_agg`) and shipped the identical
architecture, plus one move ours lacks.

| project | sql side | js side |
| --- | --- | --- |
| drizzle v1 "codecs" | `castInJson` → `${col}::text` | `normalizeInJson` → parse it back |
| postgrest | `::TEXT` before `to_json` | the consumer's |
| this repo | — | `asFromDatabase.date` · `asFromDatabase.number` |

⇒ nobody escaped the js layer. the sql cast does not replace the js cast; it feeds it a lossless input.

## .the gap, precisely
`defineQuerySelectExpressionForSqlSchemaProperty.ts` nests a bare column reference:

```sql
json_build_object('id', price.id)          -- ours: a json number
json_build_object('id', price.id::text)    -- drizzle's: a string, full precision
```

a json number is an ieee-754 double once `JSON.parse` runs, so a `bigserial` past `2^53` loses
precision before any cast sees it. that is why the number cast **throws** on an unsafe integer.

## .what it buys — one case of four
| divergence | `::text` | js cast still owed? |
| --- | --- | --- |
| `timestamptz` in json | string, not a `Date` | yes |
| `numeric` in json | string, not a `number` | yes |
| **`bigserial` past `2^53` in json** | **string, precision kept** | yes, to parse it |
| the upstream `Record<string, any>` for a nested column | untouched | yes |

⇒ one edge case moves from a loud throw to a correct read. the js casts need no change — each
already accepts a string.

## .the shape of the fix
append `::text` to the nested column reference at the two `DIRECT_BY_NESTING` sites (solo, array),
for NUMBER properties. the `...OutputJsoned` type widens `number` → `string` for those — a truer type.

🔴 NUMBER only until DATE is settled. `timestamptz::text` renders per the session's `DateStyle`,
where json's serializer is fixed iso-8601. candidates: `to_json(col)#>>'{}'`, or `to_char(...)`.

## .why it is not done in this round
not SAFE and not CLEAN: it changes generated **sql**, which lands in provisioned
`view_*_hydrated.sql`, so every consumer migrates. a `fix` that needs a migration is not a `fix`.
and the case it repairs already fails loud, which is the bar this route set.

🟡 the vision refused a wider version (text on both paths) on the same migration grounds. this one is
narrower — json only — so argue the refusal fresh rather than inherit it.

⇒ read beside `v2026_09_21.feat.map-branded-nominals-to-their-true-column-types.md`, which would shrink
the DATE half.
